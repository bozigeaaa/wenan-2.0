# 新闻发现“直接进站优先＋外部检索补漏”设计

## 目标

保留现有 P0—P4 新闻渠道主次顺序，同时改变每一级渠道的实际查找方式：优先直接进入对应网站检查站内内容，再使用网页检索工具、其他搜索引擎或新闻聚合入口补漏。避免把通用检索结果误报成已经访问 Google、X、MEED、Etimad 或其他具体渠道。

## 三套规则分别负责什么

1. `P0—P4` 决定新闻发现时先查哪些渠道。
2. “直接进站优先＋外部检索补漏”决定如何检查这些渠道。
3. `A/B/C` 决定候选信息能否作为事实证据。

三套规则互不替代。发现顺序不等于证据等级；检索工具命中某个网站，也不等于已经直接检查该网站。

## 渠道顺序

保留现有顺序：

- P0：Google / Google News、X、MEED、Etimad。
- P1：沙特当地媒体。
- P2：项目业主、主管机构和企业官网。
- P3：中东专业媒体和项目数据库。
- P4：国际媒体及其他可追溯来源。

P0 没有合格候选时，再依次扩展 P1—P4。若某渠道受登录、付费墙、地区或技术限制，必须记录为未完成访问，不能写成“没有新闻”。

## 每一级的查找方式

对当前优先级中的渠道，按以下顺序执行：

1. 直接进入网站。
2. 检查站内搜索、最新新闻、主题分类、公告页、项目页、新闻归档或可用 RSS。
3. 记录实际检查的入口、检索词、日期和访问结果。
4. 再使用网页检索工具、Google、Bing、新闻聚合入口或 `site:` 定向查询补漏。
5. 外部检索发现的新线索仍须打开原文；只看到搜索摘要时不能进入核验卡。

Google / Google News 作为 P0 渠道时，只有实际打开其页面、执行查询并查看结果，才能记录为“已直接访问”。通用网页检索工具返回的结果只能记录为“外部检索线索”。同样的记录边界适用于 X、MEED、Etimad及其他具体网站。

## 核验规则

候选出现后立即进入原有 A/B/C 核验流程，不必等 P1—P4 全部查完：

- 优先回到政府、监管机构、Etimad、项目方、企业或其他原始公告核实事件。
- 重大事实在可行时补充一个独立的当地媒体、专业媒体或通讯社来源。
- 搜索结果、聚合页、社交帖子和二次转述只作发现线索，不能单独证明关键事实。
- 一手公告只能证明其明确写出的内容，不能自动扩展到全行业、全部项目或公司参与关系。

## 检索记录

新闻搜集反馈中的渠道记录应区分：

- `直接访问完成`：实际进入网站并检查站内内容。
- `外部检索线索`：由网页检索工具、其他搜索引擎或聚合入口发现。
- `访问未完成`：登录、付费墙、地区或技术限制导致无法完成检查。

禁止把“检索工具命中某网站”写成“已检查该网站”，也禁止声称使用了未实际访问的 Google、Google News、X、MEED、Etimad、Bing或其他渠道。

## 修改范围

- 更新 Git 仓库内的热点新闻 Skill、来源规则、入口说明和规则测试。
- 将相同的新闻发现边界同步到当前 Codex 项目实际加载的 `.agents` Skill 副本，保证日常使用与 Git 仓库规则一致。
- 不改变 P0—P4 的渠道主次顺序，不改变新闻核验卡、产品适配、公司露出或 A/B/C 证据等级。
- 完成后运行全部规则测试、活动旧规则扫描和差异检查，再提交并推送 GitHub。

## 验收标准

- 规则明确写出“直接进站优先＋外部检索补漏”。
- P0 仍为 Google / Google News、X、MEED、Etimad，P1—P4 顺序保持不变。
- 通用检索工具不能冒充对具体渠道的直接访问。
- 每一级都先检查站内入口，再使用外部检索补漏。
- 发现渠道、访问方式和事实证据分开记录。
- 原有新闻核验、产品适配、标题、文案和 Humanizer 测试继续通过。
